01 — What it actually is

Four ideas. Everything else follows from them.

Nothing here is exotic — this is the same shape RocksDB, Cassandra, and every serious time-series database use. What matters is that every piece of it is built and tested from scratch, not imported.

Durability

Write-ahead log

Every write is a sequential append to a log before it touches memory. A failed append leaves no trace behind — which is what makes retrying a write safe.

Storage

Sorted string tables

When the in-memory table fills up, it's flushed to an immutable, prefix-compressed file with a bloom filter — written once in a single forward pass, never modified again.

Consistency

MVCC via sequence numbers

Every key carries a version. An overwrite or a delete is a new record, never a mutation — which is exactly what lets concurrent reads run with zero locks.

Recovery

Tested by construction

Recovery doesn't just run after a crash — it runs on every single open, including a clean one. The path that matters most is the path that's actually exercised.

02 — The problem it solves

Most databases update records in place. strata never does.

In-place updates are simple until durability meets heavy random writes — every update is a random-access disk write, and if you want it durable, an fsync to match. strata's entire design comes from refusing that trade: an overwrite is a new record, a delete is a new record. Nothing is ever modified where it sits.

What that buys you

Writes become cheap — one sequential log append, one in-memory insert. Concurrency becomes cheap — nothing a reader is looking at can be mutated out from under it, so readers take zero locks.

What it costs you

Reads become more expensive — a key might live in several files, so a lookup can touch more than one. Space becomes more expensive — old versions and tombstones sit on disk until compaction reclaims them.

Right shape when writes dominate and you want random writes turned sequential on the device — the exact workload this demo below generates. Wrong shape when you need bounded read latency with zero tuning; a B-tree wins there.

03 — How it works

The write path and the read path

Every write lands in the log before the memtable, so a crash between the two never loses an acknowledged write. Every read checks memory first, then files newest-to-oldest, stopping at the first version it finds.
