B-tree vs LSM-tree

Most databases you've used — SQLite, Postgres, MySQL — update records in place with a B-tree. strata never does. Pick a side below and watch what each one actually does to a write.

B-tree

  • Update mutates the record where it already sits on disk
  • Write is random I/O — every insert can land on a different page
  • Read is one predictable path — O(log n) down a single tree
  • Concurrency needs locks or latches — readers and writers can collide on the same page
  • Used by SQLite, PostgreSQL, InnoDB

LSM-tree

  • Update appends a new version — the old record is never touched
  • Write is sequential I/O — one log append, one memtable insert
  • Read checks memory, then files newest-first, until it finds a match
  • Concurrency is free — nothing a reader is looking at can be mutated under it
  • Used by RocksDB, Cassandra, LevelDB — and strata
There's no free lunch

What each shape actually costs

Write cost
B-tree pays random I/O per write. LSM turns it sequential.
Read cost
A key can live in several files. Bloom filters claw most of it back.
Space cost
Old versions and tombstones sit around until compaction — phase A3, not built yet.

Right shape when writes dominate and you want random writes turned sequential on disk — exactly the workload the playground generates. Wrong shape when you need bounded read latency with zero tuning; a B-tree wins there.

strata — phase A1 of 6. Write path, durability, crash recovery. Zero dependencies.
